# Standalone migration plan (planning only)

Status: **plan, not implementation.** The benchmark cleanup did not port any
tool, change any handler behavior, remove any tool, or change security. This
document records the current architecture, the target boundaries, and the order
of work for making `@fraziym/mcp` the canonical standalone tool server for all
Fraziym products.

## 1. Current architecture (source-grounded)

- **Catalog / discovery:** `catalog.json` is generated by
  `scripts/gen-catalog.ts` and answered directly for `tools/list`;
  `LazyToolHost` (`src/core/host.ts`) builds only the family a call needs via
  memoized dynamic imports (`src/core/families.ts`).
- **Groups / composition:** `src/groups/axoniz.ts` (72 tools, static imports of
  `@fraziym/axoniz/memory` and `@fraziym/axoniz/tools`) and
  `src/groups/xorvoid.ts` (25 tools, also static Axoniz imports). The default
  group is `all` (74 catalog tools).
- **Tool wrappers:** `src/tools/*.ts` register schemas/handlers. File, shell,
  web, code, computer and memory wrappers call Axoniz classes
  (`FileTools`, `ShellTools`, `WebTools`, `CodeTools`,
  `ComputerTools`, `UnifiedMemory`). Git tools are local wrappers around the
  `git` CLI. Axodex tools shell out to the `axodex` CLI resolved from
  `@fraziym/axodex`, PATH, or `npx --no-install`.
- **Agent-runtime stubs:** `src/tools/stubs.ts` advertises 10 goal/swarm tools
  that return explicit `[ERROR] ... requires the axoniz agent runtime`.
- **Protocol:** `src/protocol/server.ts` + `src/protocol/http.ts` implement
  JSON-RPC 2.0, dual-era MCP (`2026-07-28` stateless + legacy
  initialize/sessions/SSE), stdio and Streamable HTTP. `src/cli/serve.ts` wires
  CLI options and the conformance fixture surface.
- **Guard:** `src/core/guard.ts` provides workspace realpath containment, path
  argument caps, output truncation, secret-redacted audit log. HTTP adds
  loopback binding, Origin checks, bearer auth and rate limiting.
- **Gateway:** `src/gateway/*` adds 13 `router_*`/`fix_*`/`brain_*` endpoints
  behind `--router-tools` (87 advertised with the flag).
- **Dependency shape today:** `package.json` depends on
  `@fraziym/axoniz: >=0.1.8-beta.1`. Axoniz has a **non-optional peer**
  `@fraziym/axodex`, so both install together (observed cold install: 140.9 s,
  1,305.6 MB, 18,115 files). Axoniz also brings `node-llama-cpp`, tree-sitter
  packages and `@ladybugdb/core`.

## 2. Target boundaries

Keep the protocol/server layer separate from the reusable tool implementation
layer:

| Layer | Owns | Must not own |
| --- | --- | --- |
| `protocol` | JSON-RPC framing, MCP versions, stdio/HTTP transport, SSE/session, conformance fixtures | tool business logic, product imports |
| `core` | catalog, lazy host, guard, audit, error/meta contracts | transport details, Axoniz/Axodex classes |
| `tools` | schemas, handlers, result normalization, per-tool requirements | group composition, CLI parsing |
| `integrations` | adapter implementations for Axoniz/Axodex/native capabilities | MCP protocol, catalog generation |
| `groups` | named, versioned tool sets for consumers | hidden runtime coupling |

Dependency rules:

- `tools` and `core` must not import `groups`, `protocol`, `gateway` or the CLI.
- Consumer-facing groups may import tools; integrations may import the external
  package only inside an adapter module.
- No circular dependencies; no per-call dynamic import of a product internals
  path that is not behind an interface.
- Optional/heavy capabilities (axodex, computer, memory backends, native
  modules) are loaded lazily by the tool family that needs them, never at
  `serve` startup or `tools/list`.

## 3. Tool ownership and contracts

- MCP owns every advertised tool name, schema, description, annotations,
  guard policy and error contract. Axoniz/Axodex/Xorvoid become implementation
  details or optional integrations.
- Behavior must match the current wrapper surface unless a change is
  deliberate and documented. The `[ERROR] <tool>: <message>` string contract
  (handlers never throw to the agent loop) is part of the public contract.
- `docs/development/tool-inventory.md` is the authoritative 74-tool map. Every
  row must end in one of: ported implementation, adapter-backed
  implementation, or explicit non-silent unsupported/deprecated status.
- The 10 agent-runtime stubs are the first explicit product decision: implement
  the underlying capability, keep the explicit unsupported error, or remove
  them with a versioned deprecation. They must not silently disappear.
- Schemas get stable identities: adding required fields is breaking; optional
  fields and new tools are additive. Catalog generation stays deterministic.
- Memory/code intelligence: define a storage/backend interface (KV, palace,
  KG, diary, code graph) instead of importing `UnifiedMemory` classes
  directly; keep path configuration (`memoryPaths`, env overrides) validated
  and workspace-scoped by default.

## 4. Optional/heavy dependencies

- Split install profiles: core server (no Axoniz), storage/memory,
  computer/desktop, code intelligence. A product that only needs file/git/web
  tools should not download 1.3 GB.
- Native modules (`node-llama-cpp`, tree-sitter, `@ladybugdb/core`,
  `screenshot-desktop`, `sharp`) must be optional and imported only on first
  use of their family.
- Axodex must be optional: axodex tools report a clear "axodex not installed"
  error, not an install failure. Do not make `axodex` a peer of the core
  package.
- Version ranges must be explicit and tested (replace the unbounded
  `>=0.1.8-beta.1` before the core no longer depends on Axoniz).
- Shared-dependency idea for later: install one versioned Fraziym runtime under
  `%LOCALAPPDATA%\FRAZIYM\runtime` / `~/.fraziym/runtime` with a manifest, and
  have products spawn the MCP server or consume a peer/workspace dependency.
  ESM does not resolve arbitrary shared directories; `NODE_PATH` is not a
  reliable ESM solution. This is a packaging decision, not a code shortcut.

## 5. Security and isolation

- Preserve the workspace jail, realpath containment, path/arg caps, output
  truncation, redacted audit log, HTTP Origin/binding/auth/rate-limit rules.
- Integration code must not bypass `guardToolbox`; adapters receive the
  workspace and cannot widen it.
- Memory backends must not silently write outside their configured paths.
- Add regression tests for every adapter boundary; no security weakening is an
  acceptance blocker.

## 6. Packaging, discovery and compatibility

- `tools/list` remains answerable from the catalog without importing any
  family; keep catalog/tool parity tests.
- Keep default 74 and `--router-tools` 87 behavior stable until a versioned
  change says otherwise.
- Keep `axonizTools`/`xorvoidTools` exports working during migration; mark
  deprecated only with a release note and a replacement path.
- CLI command set stays compatible; only benchmark-only commands were removed
  in this cleanup (`bench`). `prove`, `fuzz`, `serve`, `tools`, `call`,
  `doctor`, `install`, `version` remain.
- Clean install must work from the published package on Windows, macOS and
  Linux. The current `latest` npm tag has no `bin`; use `beta` until the
  next publish. Track the fix as a release task, not a doc workaround.
- Observed 2026-10-19: a fresh prefix install of the local tarball added 360
  packages in 3 min, and an isolated launch answered `tools/list` with 74 tools
  and ran `get_time`/`file_write`/`file_read` (see
  [evidence/clean-install-2026-10-19.md](./evidence/clean-install-2026-10-19.md)).
  Native install scripts (tree-sitter grammars, `@ladybugdb/core`,
  `node-llama-cpp`) were **not authorized** in that consumer prefix; the package's
  `allowScripts` does not propagate to consumers. This is part of the optional
  dependency work.
- No public benchmark index, leaderboard or scoring is maintained. Verification
  stays in `prove`, `fuzz`, tests and the conformance artifact.

## 7. Migration order (proposed)

1. Freeze this inventory and the acceptance checklist; add a test that every
   catalog name maps to a known owner/status.
2. Introduce the transport-independent tool contract and integration
   interfaces; make no behavior changes.
3. Move the already-local tools (git family, `get_time`, `done`) behind the
   contract first, preserving schemas and guard behavior.
4. Convert the Axoniz-backed wrappers behind adapters, starting with
   file/shell/web, then code/computer, then memory.
5. Make Axodex and native/desktop capabilities optional install profiles with
   explicit unavailable errors.
6. Decide the 10 agent-runtime stubs (implement/keep explicit/remove with
   deprecation).
7. Verify the core server runs with no `@fraziym/axoniz` installed, then switch
   other Fraziym products to MCP and remove their duplicated tool layers.
8. Run the acceptance checklist and publish a versioned migration note.

## 8. Open risks

- Memory/code-intelligence behavior is currently Axoniz-owned; extraction may
  reveal undocumented storage assumptions.
- Desktop automation and native modules are OS-specific and hard to test in
  CI; they need an explicit unsupported/degraded path.
- The 10 stubs and the `axonizTools` group are a compatibility surface; any
  removal can break consumers of the current package.
- Shared-dependency installation is unresolved; do not promise it before a
  packaging prototype proves ESM resolution and upgrade behavior.
- Axoniz is not in this repository, so interface contracts must be negotiated
  and pinned; avoid copying Axoniz internals into MCP.
